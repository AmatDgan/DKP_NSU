# Запуск сайта в интернет: GitHub, домен, защита

Документ отвечает на три вопроса: (1) что сейчас с GitHub, (2) как выложить
сайт в интернет и привязать домен, (3) насколько он защищён и что я уже усилил.

---

## 1. GitHub: честный статус (прочитайте первым)

**Нет, ваши изменения сейчас НЕ попадают в GitHub автоматически.**

Я работаю с файлами проекта в папке на вашем Mac. В GitHub лежит **старая
версия** — последний коммит от **22 мая 2026** («вернуть оригинальный дизайн»).
Всё, что мы сделали после этого (чат поддержки, гейт ИППК, расширенная и
редактируемая админ-панель, блок повторной регистрации, новая культурная
программа, новая шапка, защита) — это **17 несохранённых изменений**, которые
живут только в папке на компьютере и в GitHub **не выгружены**.

**Почему я не могу выгрузить сам:**

1. Публикация в ваш GitHub требует **ваших** учётных данных (логин/токен) —
   их у меня нет и не должно быть, это ваш аккаунт.
2. Среда, в которой я работаю, не имеет прав записи в служебную папку `.git`
   вашего репозитория (и там остался «замок» — файл `.git/index.lock`).

Итог: **коммит и push делаете вы на своём Mac.** Это нормальная и правильная
схема — так и должно быть.

### Как выгрузить всё в GitHub (команды для Терминала на Mac)

```bash
cd ~/Documents/Claude/Projects/"Проект ЦБ"

# 1) убрать застрявший замок (если команды git выдают ошибку про index.lock)
rm -f .git/index.lock

# 2) посмотреть, что изменилось
git status

# 3) добавить все изменения и сохранить
git add -A
git commit -m "Чат поддержки, ИППК, редактируемая админка, дизайн, защита"

# 4) выгрузить в GitHub
git push origin main
```

GitHub попросит логин и токен — это и есть та самая защита: публиковать в ваш
репозиторий можете только вы.

> ⚠️ Перед `git push` убедитесь, что в репозиторий **не** попадают `.env` и
> файл базы `prisma/dev.db`. Это уже настроено в `.gitignore` и проверено —
> секреты и данные в GitHub не уходят. После `git status` их быть не должно
> в списке.

## 2. Как выложить сайт в интернет и купить домен

Сайт написан на Next.js — для него идеально подходит **Vercel** (бесплатно для
такого проекта, и каждый `git push` будет сам обновлять сайт).

### Шаг А. База данных в облаке — это ОБЯЗАТЕЛЬНО до публикации

Сейчас данные участников хранятся в файле `prisma/dev.db` на вашем компьютере.
На Vercel такой файл **не работает** (сервер «без диска», данные будут
теряться). Поэтому до запуска базу нужно перенести в облако:

1. Завести бесплатный Postgres на https://neon.tech (вход через GitHub).
2. Скопировать строку подключения (`DATABASE_URL`).
3. Сообщить мне — я переведу код с SQLite на Postgres (часть запросов сейчас
   написана под SQLite, их нужно адаптировать; это работа на моей стороне).

Без этого шага сайт откроется, но регистрации не будут сохраняться.

### Шаг Б. Развернуть сайт на Vercel

1. Зарегистрируйтесь на https://vercel.com через свой GitHub.
2. **Add New → Project** → выберите репозиторий `AmatDgan/DKP_NSU`.
3. В **Environment Variables** добавьте (это секреты, в код они НЕ пишутся):
   - `DATABASE_URL` — строка из Neon (шаг А),
   - `AUTH_SECRET` — длинная случайная строка. Сгенерировать в Терминале:
     `openssl rand -base64 32`,
   - `AUTH_URL` — адрес сайта (сначала временный `https://<проект>.vercel.app`,
     позже — ваш домен).
4. **Deploy.** Через пару минут сайт будет доступен по адресу
   `https://<проект>.vercel.app`.

С этого момента каждый ваш `git push` автоматически обновляет сайт в интернете.

### Шаг В. Купить домен и привязать его

Домен я купить за вас не могу (это оплата и регистрация аккаунта). Покупаете вы:

1. Выберите регистратора: например **reg.ru**, **Cloudflare**, **Namecheap**.
   Для красивого имени подойдёт что-то вроде `dkp-nsu.ru` (`.ru` оформляется
   у российских регистраторов).
2. Купите домен (обычно 200–1500 ₽/год для `.ru`).
3. В Vercel: проект → **Settings → Domains** → введите купленный домен.
   Vercel покажет, какие DNS-записи прописать у регистратора (обычно один
   `CNAME` или `A`-запись).
4. Пропишите эти записи в панели регистратора. Через несколько часов домен
   заработает, HTTPS Vercel подключит автоматически и бесплатно.
5. Обновите переменную `AUTH_URL` в Vercel на ваш домен.

## 3. Защита от взлома: что уже сделано и что осталось

Честно: **никто не может пообещать «100% защиту от любых хакеров»** — так не
бывает ни у кого, включая банки. Но сайт можно привести к крепкому
профессиональному уровню, на котором типовые атаки закрыты. Часть я уже
внедрил в этот раз.

### Что я добавил сейчас (в коде)

- **Заголовки безопасности** на все страницы (`next.config.mjs`):
  запрет встраивания сайта в чужие iframe (защита от clickjacking), запрет
  MIME-sniffing, строгая политика реферера, отключение доступа к камере/
  микрофону/геолокации, принудительный HTTPS (HSTS), скрытие признака
  «сделано на Next.js».
- **Ограничение перебора (rate limiting):**
  - вход — не более 8 попыток за 5 минут с одного IP;
  - отправка анкеты — не более 12 за 10 минут с IP.
  Это резко затрудняет подбор паролей и спам форм.

### Что уже было устроено правильно (проверено ранее)

- Пароли хранятся не в открытом виде, а как **bcrypt-хэш**.
- Сессии подписаны секретным ключом; подделать вход без ключа нельзя.
- Запросы к базе **параметризованы** — SQL-инъекции закрыты.
- Доступ к админке проверяется по роли на сервере, а не только прячется в меню.
- `.env` и база **не** уходят в GitHub.

### Что обязательно сделать перед публичным запуском

1. **Сильный `AUTH_SECRET`** в переменных Vercel (через `openssl rand -base64 32`),
   и больше нигде его не хранить.
2. **Перенос базы в облачный Postgres** (раздел 2, шаг А) — иначе данные на
   проде не сохраняются, плюс облачная БД делает бэкапы.
3. **Сменить пароль первого администратора** на длинный и уникальный (тот, что
   в `.env` для разработки, на проде использовать нельзя).

### Что усилить следующим шагом (по желанию, повышает уровень)

- **Rate limiting через Upstash Redis** — общий счётчик на все серверы Vercel
  (текущий — в памяти одного инстанса, это «первый рубеж»).
- **Двухфакторный вход для админов** (код на e-mail) — снижает ущерб при
  утечке пароля админа.
- **Журнал действий админов** — кто что менял; полезно, раз админов будет
  несколько.
- **Регулярные бэкапы базы** (Neon делает, стоит включить экспорт).

Главный организационный риск — не код, а **раздача прав администратора**:
каждый админ видит все персональные данные. Давайте роль точечно, у каждого —
свой аккаунт с сильным паролем, и снимайте роль сразу, когда доступ больше
не нужен.
