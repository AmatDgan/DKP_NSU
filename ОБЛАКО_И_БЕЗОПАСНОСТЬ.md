# База данных в облаке и безопасность данных

Документ отвечает на два вопроса: (1) как сделать так, чтобы база участников
жила в облаке, а ваш Mac в ней «не фигурировал», и (2) насколько мы защищены
от взлома и утечки данных и что ещё нужно усилить.

---

## 1. Главное, что нужно понять про «всё в Git»

Git — это хранилище **кода**, а не **базы данных пользователей**.
Заливать в Git живую базу с персональными данными участников — нельзя,
и вот почему:

- Git хранит всю историю навсегда. Если данные хоть раз попали в репозиторий,
  удалить их «насовсем» крайне сложно — они остаются в истории коммитов.
- Любой, кому вы дадите доступ к репозиторию (а вы планируете добавлять
  админов-знакомых), получит **полную копию** всех персональных данных к себе
  на компьютер. Это прямое нарушение 152-ФЗ «О персональных данных».
- При публичном репозитории данные утекут моментально.

Поэтому правильная архитектура такая:

```
┌─────────────┐      ┌──────────────────┐      ┌────────────────────┐
│   GitHub    │      │   Хостинг (сайт) │      │  Облачная БД        │
│  только КОД │ ───▶ │   Vercel         │ ───▶ │  Postgres (Neon)    │
└─────────────┘      └──────────────────┘      └────────────────────┘
   код виден            сайт работает              данные участников
   админам              без вашего Mac             здесь, отдельно от кода
```

- **Код** — в Git/GitHub. Его видят админы, он не содержит данных.
- **Сайт** — на хостинге (Vercel), запускается в облаке. Ваш Mac не нужен,
  чтобы сайт работал.
- **Данные участников** — в облачной базе (Postgres). Доступ к ней — только
  по секретному паролю (строке подключения), который **не** лежит в Git.

Сейчас у нас уже сделано правильно: секреты (`.env`) и файл базы
(`prisma/dev.db`) **исключены из Git** (см. `.gitignore`) и в историю
никогда не попадали. Это проверено.

---

## 2. Что уже безопасно сейчас

- `.env` (секрет подписи сессий, пароль первого админа) — **не в Git**.
- Файл базы `prisma/dev.db` — **не в Git**.
- Пароли пользователей хранятся не в открытом виде, а как **bcrypt-хэш**
  (расшифровать обратно нельзя).
- Сессии подписаны секретным ключом (`AUTH_SECRET`); подделать cookie
  без ключа невозможно.
- Доступ к админ-панели и API проверяет роль `ADMIN` на сервере, а не
  только прячет кнопки в интерфейсе.
- Согласие на обработку ПДн (152-ФЗ) фиксируется с датой.

**Минус текущей схемы:** база — это файл `dev.db` на вашем Mac. Пока сайт
крутится на вашем компьютере, данные физически у вас. Чтобы Mac «не фигурировал»,
нужно перенести и сайт, и базу в облако (раздел 3).

## 3. Перенос в облако — пошагово

Эти шаги делаются **один раз**. Аккаунты регистрируете вы (я не могу
создавать учётные записи за вас), а я подготовил код так, чтобы переход
прошёл с минимумом правок.

### Шаг 1. Облачная база Postgres (Neon — бесплатный тариф)

1. Зарегистрируйтесь на https://neon.tech (вход через GitHub).
2. Создайте проект → получите строку подключения вида
   `postgresql://user:password@host/dbname?sslmode=require`.
3. Сохраните её — это и есть `DATABASE_URL` для облака.

Альтернатива — Supabase (https://supabase.com), тоже даёт Postgres бесплатно.

### Шаг 2. Переключить проект с SQLite на Postgres

В `prisma/schema.prisma` поменять провайдер:

```prisma
datasource db {
  provider = "postgresql"   // было: "sqlite"
  url      = env("DATABASE_URL")
}
```

> ⚠️ Важный технический момент. Сейчас часть кода (таблицы `Application`
> и `SupportMessage`) использует «сырой» SQL с приёмами, специфичными для
> SQLite (`PRAGMA table_info`, `BOOLEAN 0/1`). При переходе на Postgres эти
> места нужно будет адаптировать — это работа на моей стороне, дайте знать,
> когда заведёте облачную базу, и я переведу проект на Postgres-миграции
> Prisma (`prisma migrate`) начисто. Тогда схема будет создаваться
> автоматически и одинаково локально и в облаке.

### Шаг 3. Хостинг сайта на Vercel

1. Зарегистрируйтесь на https://vercel.com через GitHub.
2. «Import Project» → выберите репозиторий `AmatDgan/DKP_NSU`.
3. В настройках проекта → **Environment Variables** добавьте (НЕ в код!):
   - `DATABASE_URL` — строка из Neon (шаг 1),
   - `AUTH_SECRET` — длинная случайная строка (сгенерировать:
     `openssl rand -base64 32`),
   - `AUTH_URL` — адрес сайта, например `https://dkp-nsu.vercel.app`.
4. Deploy. Сайт поднимется в облаке и будет работать **без вашего Mac**.

После этого каждый `git push` в GitHub будет **автоматически** разворачивать
новую версию сайта (это и есть «автоматическая выгрузка», которую вы хотели) —
но выгружается **код**, а данные остаются в защищённой облачной базе.

### Шаг 4. Команды Git (выполнять на Mac, не в этом окне)

Я подготовил и проиндексировал изменения, но закоммитить из этой среды нельзя —
доступ к служебной папке `.git` ограничен, и публикация в ваш GitHub требует
ваших учётных данных. Откройте Терминал на Mac в папке проекта и выполните:

```bash
cd ~/Documents/Claude/Projects/"Проект ЦБ"
git add -A
git commit -m "Чат поддержки, ИППК-гейт, редактируемая админ-панель, культурная программа"
git push origin main
```

GitHub попросит логин/токен — это нормально, так и должно быть: только вы
можете публиковать в свой репозиторий.

## 4. Безопасность: можно ли нас взломать и как защищаемся

Коротко: при правильном развёртывании (раздел 3) типовые атаки закрыты.
Ниже — как именно злоумышленник мог бы пытаться, и что этому противостоит.

### Как могут пытаться и что мешает

1. **Подбор/кража cookie сессии.**
   Сессии подписаны `AUTH_SECRET`. Без него подделать вход нельзя.
   *Условие:* `AUTH_SECRET` должен быть длинным, случайным и лежать **только**
   в переменных окружения хостинга, никогда — в коде или Git.

2. **SQL-инъекция** (попытка через форму выполнить вредоносный запрос к базе).
   Запросы используют параметры (`?`-плейсхолдеры), а не склейку строк, —
   пользовательский ввод не попадает в тело SQL. Это закрывает инъекции.

3. **Брутфорс паролей** (перебор на странице входа).
   Пароли проверяются по медленному bcrypt-хэшу. **Чего не хватает:** лимита
   попыток входа (rate limiting). См. раздел 5, пункт 1 — это надо добавить.

4. **Перехват трафика** (чтение данных «в пути»).
   На Vercel сайт работает по HTTPS по умолчанию; cookie помечены
   `Secure`+`httpOnly`. Перехват и кража cookie из JS закрыты.

5. **Доступ к чужим данным через API** (подставить чужой `userId`).
   API поддержки и анкеты берут `userId` из проверенной серверной сессии,
   а не из того, что прислал браузер; админские эндпоинты требуют роль `ADMIN`.

6. **Утечка через репозиторий.**
   Самый частый путь утечки у небольших проектов — случайно закоммитить `.env`
   или базу. У нас они в `.gitignore` и в историю не попадали (проверено).

### Где основной риск именно у вас

Главный организационный риск — **не код, а доступы**: вы планируете сделать
админами знакомых. Каждый админ видит все персональные данные участников.
Поэтому:
- давайте роль `ADMIN` только тем, кому реально нужно;
- у каждого админа — отдельный личный аккаунт с сильным паролем
  (не один общий логин на всех);
- при уходе человека — снимайте роль (в админ-панели) сразу.

## 5. Что усилить дальше (вектор развития)

По убыванию важности для защиты данных:

1. **Ограничение попыток входа (rate limiting).**
   Сейчас страницу `/auth/login` можно дёргать без лимита. Добавить
   ограничение (например, 5 попыток в минуту на IP) — закрывает перебор
   паролей. Можно через middleware или сервис вроде Upstash Ratelimit.

2. **Двухфакторная аутентификация для админов.**
   Минимум — подтверждение по e-mail-коду при входе админа. Резко снижает
   ущерб от утечки пароля админа.

3. **Журнал действий админов (audit log).**
   Записывать, кто из админов что менял/смотрел. При большом числе админов
   это и дисциплинирует, и помогает разобраться при инциденте.

4. **Резервное копирование базы.**
   Neon/Supabase делают бэкапы, но стоит включить регулярный экспорт, чтобы
   данные не пропали при сбое.

5. **Политика паролей и сброс пароля.**
   Сейчас минимум 8 символов. Добавить проверку на слишком простые пароли
   и страницу восстановления доступа по e-mail.

6. **Согласие и срок хранения данных (152-ФЗ).**
   Прописать, сколько хранятся данные и как участник может попросить их
   удалить; добавить кнопку удаления своей анкеты в личном кабинете.

### Улучшения по продукту (не про безопасность)

- Экспорт списка участников в Excel/CSV из админ-панели — для оргкомитета.
- Уведомления на e-mail участнику при изменении статуса заявки.
- Напоминания о дедлайне регистрации.
- Страница «Программа по дням» с расписанием секций и лекций.
